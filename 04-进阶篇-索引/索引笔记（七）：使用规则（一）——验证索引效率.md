# 索引笔记（七）：使用规则（一）——验证索引效率

> 接《索引笔记（六）：索引语法与实操》。从本篇开始进入「索引使用规则」小节，
> 顺序为：验证索引效率 → 最左前缀法则 → 范围查询 → 索引失效 → SQL 提示
> → 覆盖索引 → 前缀索引 → 单列/联合索引。
> 本篇用实测回答最基础的问题：**索引到底快多少？**
> 环境：MariaDB 13 远程开发环境，demo 库 tb_user，实测 497,587 行。

## 一、实验设计

同一张表、同一条 SQL（按 createtime 等值查询），对比「无索引」和「有索引」
两种状态下的 EXPLAIN 执行计划与真实耗时（SHOW PROFILES 计时）。

### 准备工作：确认索引现状

```sql
SHOW INDEX FROM tb_user;
```

实测发现 createtime 上**已经存在** idx_createtime（之前练习遗留）——
无法直接测"无索引"场景，于是先删除：

```sql
DROP INDEX idx_createtime ON tb_user;
SHOW INDEX FROM tb_user;   -- 确认 createtime 索引已消失，剩 7 行
```

> ⚠️ 踩坑记录：第一轮实验时没先 SHOW INDEX，直接建了个
> idx_user_createtime——结果和已有 idx_createtime **完全重复**
> （CREATE 返回了 1 warning，possible_keys 里出现两个同列索引）。
> 教训：**建索引前先 SHOW INDEX 查重；CREATE INDEX 带 warning 要警惕冗余索引**。

## 二、对照组：无索引查询（全表扫描）

```sql
SET profiling = 1;
EXPLAIN SELECT * FROM tb_user WHERE createtime = '2001-02-02 00:00:00';
SELECT * FROM tb_user WHERE createtime = '2001-02-02 00:00:00';
```

### 实测输出

```
+------+-------------+---------+------+---------------+------+---------+------+--------+-------------+
| id   | select_type | table   | type | possible_keys | key  | key_len | ref  | rows   | Extra       |
+------+-------------+---------+------+---------------+------+---------+------+--------+-------------+
|    1 | SIMPLE      | tb_user | ALL  | NULL          | NULL | NULL    | NULL | 497587 | Using where |
+------+-------------+---------+------+---------------+------+---------+------+--------+-------------+
```

```
1 row in set (0.302 sec)     -- SHOW PROFILES: 0.30203477
```

**解读**：type=ALL（全表扫描）、key=NULL（没用索引）、rows=497587
（扫了全表）、Using where（逐行过滤）——为了找 1 行数据把 49.7 万行
全部比对了一遍，耗时 0.302 秒。

## 三、实验组：建索引后再查

```sql
CREATE INDEX idx_createtime ON tb_user(createtime);   -- 实测耗时 1.05s
EXPLAIN SELECT * FROM tb_user WHERE createtime = '2001-02-02 00:00:00';
SELECT * FROM tb_user WHERE createtime = '2001-02-02 00:00:00';
```

### 实测输出

```
+------+-------------+---------+------+----------------+----------------+---------+-------+------+-------+
| id   | select_type | table   | type | possible_keys  | key            | key_len | ref   | rows | Extra |
+------+-------------+---------+------+----------------+----------------+---------+-------+------+-------+
|    1 | SIMPLE      | tb_user | ref  | idx_createtime | idx_createtime | 6       | const |    1 |       |
+------+-------------+---------+------+----------------+----------------+---------+-------+------+-------+
```

```
1 row in set (0.000 sec)     -- SHOW PROFILES: 0.00042048
```

**解读**：type=ref（非唯一索引等值查询）、key=idx_createtime、
rows=1（直接命中）。key_len=6 的构成：datetime 占 5 字节 +
该列允许 NULL 加 1 字节 = 6。

## 四、实测对比总结 ⭐

| 指标 | 无索引 | 有索引 |
|---|---|---|
| type | **ALL** | **ref** |
| key | NULL | idx_createtime |
| rows | 497,587 | **1** |
| 实测耗时 | 0.30203477 s | 0.00042048 s |

**实测加速比：0.30203477 ÷ 0.00042048 ≈ 718 倍**

对照组基准：主键查询 `WHERE id = 250000` 耗时 0.00044274s、
type=const、rows=1——主键自带聚簇索引，永远快。

## 五、底层原理：为什么差这么多

```
无索引（全表扫描）：                有索引（B+Tree 定位）：
逐行比对 497,587 次                B+Tree 3 层定位 → 拿到主键 id
  ↓                                  ↓
磁盘 IO 数千次                     回表（聚簇索引）取完整行
  ↓                                  ↓
返回 1 行                          全程 3~4 次磁盘 IO
```

索引的本质：**把"逐行比对"变成"二分定位"，用额外的空间和写入开销换查询速度**。

## 六、附带观察

1. **建索引本身要 1.05 秒**（50 万行构建 B+Tree）——索引不是免费的：
   查询快了，但 INSERT/UPDATE 时都要维护索引，这是后面索引原理篇的伏笔；
2. 实验中打错列名（createtimne）的 SQL 0.0005 秒就失败返回——
   **报错的"快"和查询的"快"是两码事**，SHOW PROFILES 里要区分；
3. 视频用 tb_sku（1000 万行）无索引查 20.78 秒，本地 50 万行只慢 0.3 秒
   ——耗时绝对值随数据量/硬件连续变化，但 **type 和 rows 的差异是确定的**，
   这才是判断索引是否生效最可靠的依据。
