# 索引笔记（十一）：前缀索引——区分度曲线、三重代价与永不覆盖的实锤

> 索引使用规则（五） · 实验数据：demo.tb_user 50 万行（name = user0~user499999 + 英雄名） · 环境：Arch Linux + MariaDB 13

## 一、什么是前缀索引

对长字符串列只索引**前 n 个字符**，用区分度换空间：

```sql
CREATE INDEX idx_name_10 ON tb_user(name(10));   -- 只索引 name 前 10 个字符
```

本表账目（name 为 varchar(50) utf8mb4）：

| 索引 | key_len 计算 | 大小 |
|---|---|---|
| 全索引 idx_user_name2 | 50×4+2 | **202 字节** |
| 前缀索引 name(10) | 10×4+2 | **42 字节**（仅 21%）|

省下的空间是真金白银，但要付出三重代价——本节全部实测。

## 二、实验 E1：区分度曲线

区分度公式：`COUNT(DISTINCT LEFT(name,n)) / COUNT(*)`

```sql
SELECT
  COUNT(DISTINCT LEFT(name,3))  / COUNT(*) AS sel_3,
  COUNT(DISTINCT LEFT(name,5))  / COUNT(*) AS sel_5,
  COUNT(DISTINCT LEFT(name,6))  / COUNT(*) AS sel_6,
  COUNT(DISTINCT LEFT(name,7))  / COUNT(*) AS sel_7,
  COUNT(DISTINCT LEFT(name,9))  / COUNT(*) AS sel_9,
  COUNT(DISTINCT LEFT(name,10)) / COUNT(*) AS sel_10,
  COUNT(DISTINCT name)          / COUNT(*) AS sel_full
FROM tb_user;
```

实测结果：

| n | 区分度 | 前缀形态 |
|---|---|---|
| 3 | 0.0001 | 'use'… 50 万行几乎全撞车 |
| 5 | 0.0001 | user0~user4，5 种 |
| 6 | 0.0002 | user0~user99，100 种 |
| 7 | 0.0020 | user0~user999，1000 种 |
| 9 | **0.2000** | user+前 5 位数字，10 万种 |
| 10 | **1.0000** | 完整 name，全不重样 |

**规律**：name = user+数字 的结构使区分度随 n 呈**几何级数跳变**——每多索引一位数字，可区分值 ×10。曲线不是平缓爬坡，陡升点就是平衡点。

**平衡点结论：n=10，key_len 42，用 21% 字节拿 100% 区分度。**

> ⚠️ 本表是合成数据，分布过于规整；真实业务的 name 不会这样，选 n 必须拿真实数据重跑公式。

## 三、实验 E2：建索引耗时（代价①现身）

```sql
CREATE INDEX idx_name_10 ON tb_user(name(10));   -- 3.149s
CREATE INDEX idx_name_9  ON tb_user(name(9));    -- 1.090s
```

**只差 4 字节，耗时差近 3 倍**——key 变长 → 每页容纳条目变少 → B+Tree 分裂维护成本上升。前缀长度的代价在建索引那一刻就开始支付。

## 四、实验 E3：SHOW INDEX 的免费复现 ⭐

```sql
SHOW INDEX FROM tb_user WHERE Key_name LIKE 'idx_name%';
```

| Key_name | Cardinality | Sub_part |
|---|---|---|
| idx_name_10 | 496,843 | 10 |
| idx_name_9 | 99,368 | 9 |

对账：

```
496843 / 500025 ≈ 0.994  ← 对应 E1 的 sel_10 = 1.0（统计采样略低）
 99368 / 500025 ≈ 0.199  ← 与 E1 的 sel_9 = 0.2000 分毫不差
```

两种独立方法测出同一个数字：E1 手动扫表 6.3 秒，SHOW INDEX 0.007 秒读出。

**⭐ 实用技巧：快速评估某列/某前缀的区分度——建个索引看 Cardinality，比 COUNT(DISTINCT) 公式法快几个数量级。**

## 五、实验 E4：三索引 EXPLAIN 对比（代价②现身）

```sql
EXPLAIN SELECT * FROM tb_user WHERE name = '吕布';
EXPLAIN SELECT * FROM tb_user FORCE INDEX(idx_name_9)  WHERE name = '吕布';
EXPLAIN SELECT * FROM tb_user FORCE INDEX(idx_name_10) WHERE name = '吕布';
```

| 版本 | key | key_len | rows | Extra |
|---|---|---|---|---|
| 默认（优化器选的） | idx_user_name2 | 202（50×4+2）✅ | 1 | **Using index condition** |
| FORCE 前缀9 | idx_name_9 | 38（9×4+2）✅ | 1 | **Using where** |
| FORCE 前缀10 | idx_name_10 | 42（10×4+2）✅ | 1 | **Using where** |

三个发现：

1. **key_len 公式再次精确对账**：前缀索引 key_len = n×4+2；
2. **前缀索引享受不到 ICP**：全索引是 Using index condition（索引层完成过滤），前缀索引退化为 Using where（必须回表后过滤）——索引里存的是截断值，无法确认整条记录是否匹配。**这是第二重代价**；
3. 优化器默认选了 202 字节的全索引而非 42 字节前缀索引：窄查询 rows=1 成本几乎相同，且全索引有 ICP。**前缀索引的收益在空间端，不在速度端。**

## 六、实验 E5：前缀索引永不覆盖（代价③，本节最硬结论）⭐

```sql
EXPLAIN SELECT id, name FROM tb_user FORCE INDEX(idx_name_10) WHERE name = '吕布';
-- key_len=42 | Using where   ← 没有 Using index！

EXPLAIN SELECT id, name FROM tb_user FORCE INDEX(idx_name_9)  WHERE name = '吕布';
-- key_len=38 | Using where   ← 同样没有
```

SELECT 的两列（id、name）在索引里"理论全都有"，却拿不到覆盖扫描。

**关键事实**：本表 name 最长 'user499999' 恰好 10 字符——idx_name_10 存的每个值都是完整的，MariaDB 依然拒绝给出 Using index。

**结论：优化器只认 Sub_part=10 的声明，不关心实际值有没有被截断。声明是前缀，就按前缀办事，一律回表。教科书"前缀索引不能覆盖索引"在 MariaDB 严格执行——即使前缀恰好等于数据全长。**

## 七、三重代价汇总

| 代价 | 实测证据 |
|---|---|
| ① 建索引慢 | name(10) 3.149s vs name(9) 1.090s，差 4 字节差 3 倍耗时 |
| ② 无 ICP | E4：前缀 Using where，全索引 Using index condition |
| ③ 永不覆盖 | E5：name(10) 存完整值仍无 Using index，Sub_part 声明说了算 |

## 八、结论卡

1. 前缀索引省空间（key_len 42 vs 202），代价是**区分度 + ICP + 覆盖**三重；
2. 选 n：跑区分度曲线找陡升点；快速评估可建索引看 Cardinality；
3. 前缀索引**永不覆盖**——哪怕前缀 = 数据全长；
4. 前缀索引价值在**空间端**（大表、长字符串列），窄查询速度差异看不出来；
5. 合成数据的曲线不能直接套生产，真实数据必须重测。

## 九、清理

```sql
DROP INDEX idx_name_9 ON tb_user;   -- 对照索引清掉，idx_name_10 留作下一节单列对照组
```
