# 索引笔记（十）：范围查询与索引截断

> 接《索引笔记（九）：覆盖索引与 SQL 提示》。范围查询实测：
> 宽范围被成本决策弃用 → 覆盖索引救场 → 窄范围截断实验挖出
> MariaDB 与 MySQL 的 ICP 计账差异。附带：createtime 第二个 25% 样本、
> key_len 类型对账新增 datetime。环境：MariaDB 13，tb_user 500,025 行。

## 一、实验矩阵与实测结果

```sql
EXPLAIN SELECT * FROM tb_user WHERE profession='软件工程' AND age=23 AND status='6';          -- R1
EXPLAIN SELECT * FROM tb_user WHERE profession='软件工程' AND age>23 AND status='6';          -- R2
EXPLAIN SELECT * FROM tb_user WHERE age>23;                                                   -- R4
EXPLAIN SELECT * FROM tb_user WHERE phone > '17799990000';                                    -- R5
EXPLAIN SELECT * FROM tb_user WHERE createtime > '2020-01-01';                                -- R6
EXPLAIN SELECT id,profession,age,status FROM tb_user WHERE profession='软件工程' AND age>23;  -- T2
EXPLAIN SELECT * FROM tb_user WHERE profession='软件工程' AND age BETWEEN 23 AND 26 AND status='6';      -- T1a
EXPLAIN SELECT id,profession,age,status FROM tb_user WHERE profession='软件工程' AND age BETWEEN 23 AND 26 AND status='6'; -- T1b
```

### 实测汇总表 ⭐

| 实验 | 条件要点 | type | key_len | Extra / 备注 |
|---|---|---|---|---|
| R1 | 三列全等值 | ref | **54** | const,const,const / rows=1 |
| R2 | 宽范围 age>23 + SELECT * | **ALL** | NULL | **成本弃用**：命中约 11 万行，回表太贵 |
| R4 | 只有 age>23 | ALL | NULL | possible_keys=NULL，最左前缀复习 |
| R5 | phone 范围（最左列+窄范围） | range | 46 | rows=23，**窄范围是好查询** |
| R6 | createtime 范围 + SELECT * | ALL | NULL | 占比 25%，possible_keys 有值但不用 |
| T2 | 同 R2 条件，SELECT 覆盖列 | **range** | 49 | **Using index，翻盘救场** |
| T1a | 窄范围 BETWEEN + status | range | **54** ⭐ | Using index condition |
| T1b | 同 T1a，覆盖版 | range | **54** ⭐ | Using where; Using index |

## 二、成本决策再现：宽范围直接 ALL（R2/R3/R6）

- `age>23` 覆盖近 90% 年龄段 → "软件工程25% × 90%" ≈ **11 万行回表**
  → 全表扫更便宜 → 优化器连 range 都不走（比截断更早一步弃用）；
- createtime > '2020-01-01' 实测 **125,287 行 = 25.05%**——与
  profession 的 25.0% 几乎相同（灌数巧合），**两个独立的 25% 成本
  决策样本**，优化器判断标准高度一致，成本决策可复现；
- **教训：范围列命中量一大，"截断"还没来得及表现，成本先判了 ALL。**

## 三、覆盖索引救场（T2/T3）

- T2：同一条 WHERE，SELECT * ALL → SELECT 索引四列变 **range + Using index**
  （11 万行免回表，成本骤降）；
- T3：createtime 覆盖版（id,createtime）同样 ALL → **range + Using index**；
- 与笔记九的翻盘实验构成**三个独立翻盘样本**，原理同一：
  **回表随机 IO 是成本账里最大的那笔，覆盖索引直接清零这笔账。**

## 四、截断实验与 ICP 计账差异 ⭐⭐（本篇核心发现）

### 结构真相（MySQL/MariaDB 一致）

age BETWEEN 23 AND 26 是 4 个值的范围，status 在每个 age 小段内散落，
**无法参与索引定位**——"范围列之后的索引列被截断"是 B+Tree 结构的必然。

### 但 MariaDB 实测 key_len=54（预期 49）

```sql
WHERE profession='软件工程' AND age BETWEEN 23 AND 26 AND status='6'
-- MariaDB 实测：range | key_len=54 | Using index condition
-- MySQL 8 教科书预期：key_len=49（status 被截断）
```

**原因：MariaDB 把 status='6' 通过 ICP 下推到索引层过滤，并把 ICP
用到的列也计入 key_len**（47+2+5=54）；MySQL 教科书记账只算"定位
用到的列"（49）。ICP 下推后不合格的行连回表都省了——
**实用性上 MariaDB 这种记账反映的过滤能力是真实存在的**。

**一句话：截断发生在"定位"，没发生在"过滤"；MySQL 的 key_len
只反映定位，MariaDB 把过滤也算进去。**

### 范围查询的两个附带观察

- ref 列恒为 NULL（范围无 const 参照值，R5/T2/T1 三处印证）；
- type 从 ref（等值）降为 range（范围）——访问类型天梯降一档。

## 五、key_len 类型对账表（累计五种类型全对上）

| 类型 | 公式 | 实测 |
|---|---|---|
| varchar(11) NULL utf8mb4 | 11×4+2+1 | 47 ✅ |
| char(1) NULL utf8mb4 | 1×4+1 | 5 ✅ |
| tinyint unsigned NULL | 1+1 | 2 ✅ |
| int NOT NULL | 4 | 4 ✅ |
| **datetime NULL（本篇新增）** | **5+1** | **6 ✅** |

## 六、rows 估算膨胀三连实锤

| 查询 | 估算 rows | 实际 | 偏差 |
|---|---|---|---|
| 覆盖版 25% 查询 | 260,898 | 125,033 | ≈2.1 倍 |
| T2 宽范围 | 199,292 | ≈110,000 | ≈1.8 倍 |
| T3 createtime 覆盖版 | 261,448 | 125,287 | ≈2.1 倍 |

**ANALYZE TABLE 执行成功后估算依旧偏差 2 倍**——低基数索引（16 种
profession）的采样误差。定论：**rows 只看数量级，不做精确对账。**

## 七、结论汇总

1. 范围列之后的索引列**无法参与定位**（结构必然，截断成立）；
2. 但截断 ≠ 失效：ICP 仍可下推过滤（MariaDB key_len 计入 ICP 列=54，
   MySQL 教科书=49）；
3. 范围命中量大时成本决策先于截断起作用（直接 ALL）；
4. 覆盖索引是范围查询的最佳拍档（三个翻盘样本）；
5. 窄范围是好查询（phone range rows=23）；
6. rows 只看数量级；ref 列范围查询恒 NULL。
