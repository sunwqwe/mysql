# InnoDB 主键索引 B+Tree 高度估算

> 配套：黑马 MySQL 课件「索引结构·思考题」 · 前置：[索引笔记（三）B+Tree 结构详解](./) · [索引笔记（五）聚簇索引与二级索引](./)

## 〇、问题

课件右上角那棵树：蓝色 = 键值、绿色 = 数据、灰色 = 指针、橙色框 = 页（Page）。
**问题：InnoDB 主键索引的 B+Tree 高度是多高？**

## 一、前提假设（课件给定）

| 假设项 | 数值 | 说明 |
|---|---|---|
| 一行数据大小 | **1k** | InnoDB 页默认 **16KB**，一页可存 **16 行**这样的数据（16 × 1k = 16k） |
| 指针大小 | **6 字节** | InnoDB 页内指向下一节点的指针固定占 6 字节 |
| 主键大小 | **8 字节** | 主键即使为 `bigint`，占用字节数为 8 |

核心思路：**非叶节点的一个槽位 = 主键(8B) + 指针(6B)**，一页 16KB 能装多少个槽位，
就决定了每个节点能扇出多少路。

## 二、高度为 2 的推导

根节点是**一页**，设它有 `n` 个主键、`(n+1)` 个指针，装满一页：

```text
n × 8 + (n + 1) × 6 = 16 × 1024
        ↓ 解方程
14n + 6 = 16384
        ↓
n ≈ 1170
```

即根节点能存 **1170 个主键、1171 个指针**——指向 1171 个叶子页；
每个叶子页存 16 行数据：

```text
1171 × 16 = 18736（行）
```

> ✅ **高度为 2 的 B+Tree ≈ 能存 1.8 万行**，约 2 万条。

## 三、高度为 3 的推导

第二层每个非叶节点同样是 16KB 一页，同样能扇出 **1171 路**：

```text
1171 × 1171 × 16 = 21,939,856（行）
```

> ✅ **高度为 3 的 B+Tree ≈ 能存 2100 万行**。

## 四、高度为 4（自行推演）

```text
1171 × 1171 × 1171 × 16 ≈ 257 亿（行）
```

## 五、结论：为什么说"三层树撑起两千万行"

| 树高 | 可存行数 | 一次查询的 IO 次数（根→叶） |
|---|---|---|
| 2 | ≈ 1.9 万 | 2 |
| **3** | **≈ 2100 万** | **3** |
| 4 | ≈ 257 亿 | 4 |

- 一般业务表到 **2000 万行级别**，B+Tree 高度仍维持 **3 层**；
- 一次主键查询 = **3 次 IO**（且根节点和第二层常驻 Buffer Pool，
  实际磁盘 IO 往往只有 1 次）；
- 这就是 B+Tree「矮胖」设计的意义——**控制树高 = 控制磁盘 IO 次数**，
  也是索引笔记（二）中"用 B+Tree 而非二叉树/红黑树"的量化收尾。

## 六、一句话总结

> 16KB 页 ÷ (8B 主键 + 6B 指针) ≈ 1170 路扇出 →
> 树高 2 存 1.9 万行、树高 3 存 2100 万行。
> **千万级大表三层搞定，查询只花 3 次 IO** —— 这就是 MySQL 选 B+Tree 的底层账本。
